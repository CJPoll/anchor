# Sabotage record — DataFlow refutable sinks: case with no catch-all, `with` `=` step (DND-5471)

- **Domain:** data_flow
- **Branch:** dnd-5471
- **Date:** 2026-11-03
- **Code under test:** `Anchor.Domain.DataFlow.Forms` (`decompose/1`'s new
  `refutable` field, `refutable_match?/1`), `Anchor.Domain.DataFlow.Builder`
  (a form statement's `Node.refutable`)
- **Suite run:** `mix test test/anchor/domain/data_flow_test.exs --timeout 5000 --max-cases 2`
  (71 tests, green before and after every row)

The architect's answer to PR #40's design question (DND-5439, Later
2026-11-03): three refutable shapes are sinks with the reason `:refutable`: a
refutable `=` (already), the scrutinee of a `case` with no catch-all clause (a
clause whose pattern is `_` or a bare variable, with no guard), and a `with`
step written with `=`. Tests first: on the unfixed code the two new positive
tests failed (`71 tests, 2 failures`: "a case with no catch-all clause is
refutable" and "a with step written with a refutable `=` is refutable").
Two existing tests used a case with no catch-all as their example (16b, "the
nodes of a dead branch"); each gained a catch-all clause so they still test
what they named.

Each mutation was applied alone to the committed code by a scratch driver
outside the repo, the suite run, and the file restored. Every row is copied
from its output.

## Not mutated, and why

- A nested `with` with a refutable `=` step inside a plain expression
  (`y = h(with {:ok, a} = f(), do: a)`) stays refutable under D: the step is
  itself a `=` node, which `refutable_match?/1`'s prewalk already found before
  this change.

## Decision recorded

- A `with` step written with `=` is refutable only when its pattern is
  (`{:ok, a} = f()`, `[b] = g(a)`); a bare-variable `=` step (`b = g(a)`)
  cannot raise, so it is not, matching the existing rule for a top-level `=`.
  The positive-control test pins it.
